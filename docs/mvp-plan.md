# MVP-план: цифровой двойник линии порошковой краски

## Цель MVP

Создать рабочее ядро цифрового двойника линии порошковой краски как первого модуля большого цифрового завода. MVP делается для одного пользователя, без личных кабинетов, ролей, сложных доступов и интеграций с реальным оборудованием.

Главный результат: можно открыть приложение, выбрать завод, цех/линию, задать параметры смены и рецептуры, увидеть модель линии, расчетный выпуск, узкие места, загрузку оборудования, риск качества и энергопотребление.

## Что важно учесть сразу

- У нас будет два завода, поэтому в модели данных сразу должен быть уровень `Factory`.
- Линия порошковой краски - это часть одного завода, а не весь продукт.
- Сейчас система offline: данные задаются вручную или seed-файлами.
- Архитектура должна позволять позже добавить другие линии, второй завод, реальные сигналы и 3D-планировку.
- MVP должен быть полезным даже без подключения к оборудованию.

## Что не делаем в MVP

- личные кабинеты;
- роли и права доступа;
- сложную авторизацию;
- интеграцию с PLC/SCADA/MES/ERP;
- полноценный 3D-редактор;
- точную физическую модель экструдера и мельницы;
- машинное обучение;
- мобильное приложение;
- мультиарендность и SaaS-архитектуру.

## Функциональный состав MVP

### 1. Карта цифрового завода

Минимальная иерархия:

```text
Company
  Factory
    Area
      Line
        Equipment
```

На первом экране:

- выбор завода;
- список производственных зон;
- карточка линии порошковой краски;
- быстрые KPI по линии.

Для второго завода пока достаточно создать пустую структуру-заготовку, чтобы архитектура не была привязана к одному объекту.

### 2. Цифровой паспорт линии

Для линии порошковой краски:

- маршрут производства;
- список оборудования;
- паспортные или demo-мощности;
- расчетная критичность оборудования;
- теги будущих сигналов;
- точки контроля качества;
- зависимости от аспирации, ОТК и фасовки.

### 3. Сценарная модель смены

Пользователь задает:

- рецептуру;
- длительность смены;
- интенсивность производства;
- размер партии;
- включена ли плановая очистка;
- условную сложность рецептуры;
- строгость качества.

Система считает:

- выпуск за смену;
- OEE-индекс;
- загрузку каждого узла;
- bottleneck;
- риск качества;
- энергопотребление;
- простую рекомендацию по ограничению.

### 4. Визуальный двойник линии

Не CAD и не тяжелый 3D на первом этапе. Нужен эффектный, но легкий интерфейс:

- схема линии;
- анимированный поток материала;
- подсветка узкого места;
- интерактивные карточки оборудования;
- тепловая индикация загрузки и риска;
- сценарные слайдеры с мгновенным пересчетом.

### 5. Справочники

Минимальные справочники:

- заводы;
- зоны;
- линии;
- оборудование;
- рецептуры;
- маршруты;
- причины простоев;
- параметры качества;
- сценарии смен.

На MVP можно хранить их в JSON или SQLite/PostgreSQL. Для скорости разработки лучше начать с JSON/SQLite, а затем перейти на PostgreSQL.

### 6. Сохранение сценариев

Нужно сохранять:

- название сценария;
- выбранную рецептуру;
- параметры смены;
- расчетные KPI;
- дату создания;
- заметку пользователя.

Это даст реальную пользу: можно сравнивать сценарии до изменения производства.

## Предлагаемый стек MVP

Самый быстрый путь:

- Frontend: React или Next.js.
- Backend: FastAPI.
- Storage: SQLite на MVP, PostgreSQL на следующем этапе.
- Simulation: собственная простая расчетная модель, затем SimPy.
- Visualization: Canvas/SVG сейчас, Three.js позже.

Почему так:

- один пользователь - не нужна тяжелая auth-система;
- SQLite достаточно для локального/первого серверного MVP;
- FastAPI хорошо подойдет для будущих расчетных и интеграционных сервисов;
- React/Next.js даст нормальный интерфейс для дальнейшего роста.

## План работ

### Неделя 1. Продуктовое ядро

- Зафиксировать модель двух заводов.
- Описать структуру первой линии порошковой краски.
- Собрать seed-данные: оборудование, маршрут, demo-рецептуры.
- Сделать основной экран: завод -> линия -> KPI.
- Убрать из интерфейса все, что не нужно одному пользователю.

Результат: приложение показывает структуру будущего цифрового завода и первую линию.

### Неделя 2. Расчетная модель линии

- Реализовать расчет смены.
- Добавить загрузку оборудования.
- Добавить bottleneck.
- Добавить OEE-индекс.
- Добавить риск качества и энергию.
- Добавить объяснение результата простым языком.

Результат: можно менять параметры смены и видеть расчет.

### Неделя 3. Сценарии и справочники

- Добавить CRUD для оборудования.
- Добавить CRUD для рецептур.
- Добавить сохранение сценариев.
- Добавить сравнение двух сценариев.
- Добавить импорт/экспорт JSON.

Результат: пользователь может вести модель без программиста.

### Неделя 4. Вау-интерфейс и демо-готовность

- Улучшить визуальную схему линии.
- Добавить тепловую карту оборудования.
- Добавить режим "смена в динамике".
- Добавить экран "паспорт линии".
- Подготовить demo-сценарии.
- Подготовить README и инструкцию запуска.

Результат: плотный MVP, который можно показывать как работающий цифровой двойник линии.

### Неделя 5-6. Укрепление MVP

- Перенести данные из JSON в SQLite/PostgreSQL, если нужно.
- Добавить API.
- Добавить журнал событий.
- Добавить простую аналитику по сценариям.
- Добавить подготовку к подключению OPC UA/MQTT без самой интеграции.

Результат: фундамент для перехода от offline-модели к connected twin.

## Минимальная версия, которую стоит считать готовой

MVP готов, если:

- есть два завода в структуре;
- есть одна детальная линия порошковой краски;
- есть список оборудования;
- есть 3-5 demo-рецептур;
- можно менять параметры смены;
- система считает выпуск, OEE, bottleneck, качество и энергию;
- можно сохранить сценарий;
- можно сравнить сценарии;
- интерфейс выглядит как командный центр, а не таблица;
- проект запускается одной командой.

## Следующий этап после MVP

После первого рабочего MVP надо решить, куда двигаться:

1. Углублять симуляцию партий.
2. Делать 3D-планировку цеха.
3. Подключать реальные данные.
4. Добавлять другие линии и второй завод.
5. Делать AI-аналитику и рекомендации.

Самый рациональный порядок: сначала сценарии и справочники, затем вторая линия/завод, затем реальные данные.
